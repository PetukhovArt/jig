# Hooks and gates

The hooks run in every project once the plugin is installed. The tools behind them run only when `.jig/config.jsonc` names them ([configuration](configuration.md)).

Each hook runs a bare `node` (Node 20 or newer) from the agent's `PATH`. On macOS an agent started from the Dock or Finder gets the launchd `PATH`, which lacks a node installed with nvm, so every hook fails: start the agent from a terminal, or link node into `/usr/local/bin`. `jig doctor` warns when `PATH` has no node or an older one.

## What works without configuration

- **Before an edit** (fails closed): a new suppression directive of ESLint, oxlint, Biome, TypeScript, stratum, ReSharper or the C# compiler (`#pragma warning disable`, `#nullable disable`) is always denied; fix the cause, only a human adds one. An edit that adds a comment to a JavaScript, TypeScript, Vue or C# file, or a test case (`it`/`test`, or a `[Fact]`, `[Theory]`, `[Test]`, `[TestCase]` or `[TestMethod]` method) to a test file, is denied once. A test file is found by its path (`*.test.*`, `*.spec.*`, `__tests__/`; for C# a folder or file name that is `tests`/`spec` or starts or ends with `Test`/`Tests`, like `TestsBackend/` or `OrderTests.cs`) or else by its content (a test of its language); it is denied once with the rules: the full `comments` or `tests` atom the first time per agent and after each compaction, a one-line reminder later. The same call passes on retry, and removing a comment or a test never stops. Tool directives a build needs (`/// <reference>`, `@vite-ignore`, webpack magic comments, `__PURE__`, `// <auto-generated>`, other `#pragma` and `#nullable` directives) are not comments for the gate.
- **After an edit**: the edit-time tools and `checks` from the config report findings on the file.
- **End of turn**: the heavy tools and `checks` from the config run over the turn's files and block the turn on an error, the chain stopping at the first failing tool. The turn's files are the session's own: the files its edit tools wrote and the files that changed while one of its shell commands ran (Claude Code: `Bash`, `PowerShell`; a background command counts until the end of the turn). A file another session or the IDE changed between those calls is not checked; the journal gets a `foreign-change` record. An agent without shell events in its adapter takes every file that changed during the turn. A project without a config takes no snapshots around shell commands. A file inside another linked worktree under the project, such as a subagent's `.claude/worktrees/agent-<id>/`, is that worktree's change and is not checked.
- **Session start**: one line when the config is invalid or the project drifted from it (a tool found but not named, a named tool without its binary), pointing to `jig init`, or `jig init --update` when a config exists.

The comment gate is on by default; a project turns it off with `"jig/comments": "off"` (suppressions stay denied), and the test gate with `"jig/tests": "off"`.

## What needs project configuration

At runtime jig reads only `.jig/config.jsonc` and `.jig/config.local.jsonc`; a tool runs only when the config names it, so without a config no tool runs. `jig init` proposes the entries from the markers it finds. Each tool resolves its marker config from the edited file upward, so a monorepo package uses its own.

| Tool | Marker config | When it runs |
| --- | --- | --- |
| `oxlint` | `.oxlintrc.json`, `oxlint.json` or `oxlintrc.json` | after each edit, errors on changed lines |
| `stratum` | `stratum.config.jsonc` | after each edit and at the end of a turn |
| `tsc` (or `"command": "vue-tsc"`) | nearest `tsconfig.json` | end of turn, errors in the turn's files only |
| `eslint` | `eslint.config.*` or `.eslintrc*` | end of turn, errors on changed lines only |
| `agent-view` | `agent-view.config.json` | `jig pre-mr`: [UI proof](ui-proof.md) before the merge request |

With `worktree.depsPool` in the config, the hooks name, once per agent, each linked worktree that has a lock file or `package.json` of npm or yarn at its root but no `node_modules` of its own (missing, or a link or junction into another checkout), with the `jig worktree seed` and `jig worktree deps` commands for it. After a shell command, only the linked worktrees that appeared while it ran are checked (a `git worktree list` before and after it); at session start and after an edit, only the linked worktree the agent's working directory is in. The hooks never install ([native worktrees](../skills/jig-slots/references/native-worktrees.md)).

Type checking is the project's job when it declares one: a root `package.json` script whose command runs `ts-decl-check` (it takes a file list) makes `jig init` propose `"tsc": false` and a check `{ "name": "types", "files": [<the project's .ts/.tsx/.mts/.cts/.vue globs>], "on": "stop", "run": "<the script's command> {files}" }`. A script named like `typecheck` that takes no file list (`vue-tsc --noEmit`) or needs a shell (`&&`, `|`) is reported and not proposed; jig's `tsc` stays.

A tool or check that times out, crashes or is cut off by the shared 110 s budget leaves the result unknown: the turn is blocked once with the rule `gate/incomplete`, which names the tool, so the agent runs it itself; a slow tool gets more time from its `timeout` ([configuration](configuration.md)).

`jig check edit <file>` and `jig check stop` run the same paths by hand. `jig check stop` prints `clean` only when every check ran to the end; otherwise it prints the findings and an `incomplete:` line, and exits 1 on an error finding, 3 when the result is unknown (the heavy checks lock busy included).
