# 13 · Architecture

**Class:** rules. **Category:** `architecture`. **Gate:** only `CONFIRMED` of the rule form ([verify](../steps/05-verify.md)). **Atoms:** `system-edges`, `domain-model`, `module-depth`, `one-way`, `shared-state`, `patterns`, `reader-cost`.

Four sections with different rule sources. The evidence in all: the quoted diff line plus the rule; what differs is where the rule comes from. Severity by section: [verify](../steps/05-verify.md#default-taxonomy).

## Section A: universal rules, always on

The rule comes from here; no project document is needed. These follow from clean architecture; they are not taste:

- **A module exports everything:** a barrel `index` re-exports internals; the interface is no narrower than the implementation. Evidence: the export line plus an outside consumer that pulls what should be hidden.
- **God object:** a module, scope or store that knows business rules, validation, formatting and wiring at once. Evidence: two lines from different responsibilities in one module.
- **Variability solved by branching in application code:** `if (brand === 'X')`, `switch (transport)` where an adapter, a registry or a capability matrix belongs (atom `patterns`). Evidence: the branching line plus the existing extension point that was bypassed (its path is required; otherwise this is angle 9).
- **Premature generalization:** an abstraction with one consumer (atoms `reader-cost`, `do-less`). Evidence: the abstraction and its only consumer.
- **The orchestrator owns state:** the composing layer holds state itself instead of wiring the owners. Evidence: the state declaration in the orchestrator plus the owner it belongs to.
- **Hidden coupling between modules:** shared mutable state, an event contract by convention, an implicit call order (atom `shared-state`). Evidence: both participants, quoted.
- **Anemic model:** rules and invariants of the domain model in the diff moved into outside functions; an illegal state is representable (atom `domain-model`). Evidence: the invariant, the outside function that holds it, and the representable illegal state.
- **A module in the wrong place:** new code went into a module or layer that does not own the concept, while an owner exists. Evidence: the added line plus the owner's path where neighbouring operations on the same concept live, or the quoted placement rule from a project document.
- **New code in a zone marked legacy.** Evidence: the mark (a comment, a README, a rule) plus the added line.
- **A list synced by hand:** the diff adds an item to a list (a registry, enum, mapping, route array) that has a second list of the same items, and the second is edited by hand or not at all. The next agent updates only the one it sees. Evidence: the added line plus the path of the second list; fix: derive one from the other, or fail the build on divergence.
- **A second way to do the same thing:** the diff introduces a new API, helper or hook for a task that already has a way, and the old one stays with its callers (atom `one-way`). Agents copy whichever way they find first, and both grow. Evidence: the new way's line plus the old way's path and its live caller. A new implementation of what exists, without the old API next to it: [angle 6](6.reuse.md).
- **Temporal decomposition:** the diff's new modules are cut by execution order (load, validate, transform, save), and one representation with its invariant is known to several of them (atom `module-depth`). Evidence: two lines in different modules relying on one representation or invariant.
- **An import bypassing the public index, or internals across a module boundary** (atom `system-edges`). Evidence: the import line plus the public entry it bypasses. The direction of layers (a lower layer imports an upper one) is not judged without a project document: it belongs to section B.

## Section B: the project's layer rules, only with a document

Layered architectures (feature-sliced design and the like) differ between projects: layers, import directions, public APIs, visibility of local shared code. A rule here comes **only as a quote from the project's architecture document** (search below). No document: section B is off, and the summary says so.

**Evidence:** the verbatim rule plus the violating line. Both required, as in [angle 10](10.conventions.md).

A rule the project's linter already enforces (restricted import paths and the like) is not flagged: the linter owns it, as it owns style.

## Section C: ADRs in force

The diff's code contradicts a decision recorded in an ADR. An ADR in the diff itself is judged here too: in the branch's tree it is already in force.

**Input: the table of contents, not the bodies.** The finder gets a list: path, title, first sentence of each ADR (where a well-formed ADR states the decision). It opens in full only those that overlap the diff in meaning. An abstract decision ("contexts talk through events") overlaps any diff that crosses a context boundary, even when it names no paths.

**Evidence:** the verbatim decision plus the violating line.

Summary: `adr: read 3 of 40` or `adr: none found`.

## Section D: the owning glossary

The diff's code names a domain concept differently from the glossary.

- a synonym from the `_Avoid_` line in an added symbol;
- a symbol named differently from the term the glossary uses for the same concept;
- a new domain concept (an exported type, state, event) without an entry in the owning glossary.

**Evidence:** the quoted glossary entry (the term and `_Avoid_`) plus the symbol line. For a concept without an entry: the symbol line plus the path of the owning glossary.

## Finding ADRs and the glossary

Walking up from the diff's directories, like the rule indexes ([step 02](../steps/02-rules.md)):

- ADRs: files `docs/adr/*.md` in every ancestor; ADRs with status `deprecated` or `superseded` are skipped. Off with `discover.adr: false` ([config](../references/project-config.md));
- glossary: the nearest `GLOSSARY.md` up from each directory (`CONTEXT.md` when there is no `GLOSSARY.md` at that level). None: section D is off.

`discover.exclude` does not apply to this search: it filters standard bodies.

## Finding the architecture document

Runs in [step 02](../steps/02-rules.md) together with the review document:

```bash
git ls-files --cached --others --exclude-standard | grep -iE 'architect|fsd|layers|boundar' | grep -iE '\.(md|html)$'
```

Take documents that describe layers, boundaries and dependency directions. ADRs do not go here: section C owns them. Summary: `architecture: docs/architecture.md (120 lines)` or `architecture: not found, section B off`.

## Not a finding

- Naming and import order: [angle 10](10.conventions.md) when the rule is written; otherwise the linter.
- "I would split it differently" without a broken rule from A or B.
- Unfortunate module boundaries without a line that breaks or duplicates because of them: a conversation, not a thread.
- A layer of pure code (a codec, a formatter, a predicate) without a broken import and without a second owner of the concept: a convention ([shape gate](../steps/05-verify.md#shape-gate)).
- A deepening proposal: not a defect ([selector](../references/selector.md#deepening)).
