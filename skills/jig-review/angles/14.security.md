# 14 · Security

**Class:** bug. **Category:** `security`. **Gate:** only `CONFIRMED`: initiator, path and effect, like the other bugs; the rare gate does not apply to security ([gates](../gates/bugs.md)). **Atom:** `system-edges`.

**Look for a sink in the diff plus a path to it from untrusted input:**

- a string reaches an executable context: `innerHTML`, `v-html`, `dangerouslySetInnerHTML`, `eval`, `new Function`, an SQL or shell command built by concatenation;
- a path or URL built from a user value without normalization: directory traversal, an open redirect, `file://` in a desktop shell;
- deserialization or parsing of external data trusted by shape: a server response field goes into code unchecked;
- a secret in the diff: a token, a password, a private key, an environment file with values;
- a removed protection: an escape, CSP, an origin check in `postMessage`, context isolation, validation at an IPC boundary;
- a permission check only on the client where the server does not do it: evidence is needed from both sides.

**Evidence:** the sink line plus **the source of the input**: where the value comes from outside (a response field, an IPC argument, a URL parameter, user input). A source inside the repository: a quote; a source outside the code's control: form 2 of the path from verify, a place, not a category.

**Severity:** `Important` by default: a hole is data loss or execution of foreign code. A secret in the diff is always `Important`; no input is required.

**Not a finding:** "maybe XSS here" without a sink in the diff; a theoretical vulnerability of a library without a call from the diff.
