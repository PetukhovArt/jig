# 8 · Efficiency

**Class:** efficiency. **Category:** `efficiency`. **Gate:** only `CONFIRMED`. **Atoms:** `effects`, `why-this-number`.

**Look for:**
- extra work on a hot path;
- CPU load the user feels: a timer or poll faster than its data changes, a handler for a high-frequency event (scroll, resize, pointer move, a socket message) doing heavy work without throttle or batching, a re-render of a whole list or tree on each item update, heavy synchronous work on the main thread that freezes the UI;
- a closure keeping a large scope alive: a leak;
- an expensive value recomputed on every call where one computation is enough;
- a deep reactive container (a deep proxy, a deep `ref`/`reactive`, a deep store) written by high-frequency events: each write tracks nested objects and wakes every dependent; the container must be shallow and updated by replacing the whole value (atom `effects`). The rate is the sum of every stream that writes the same container, not of one: three streams of a few updates a second each are one high-frequency writer. One message that mutates nested fields one by one is as many writes. A cascade multiplies the load: a dependent that is itself written (an effect or watcher that writes other state), a `deep` watcher that walks the whole object on each write, a chain of derivations. A rare stream is not a finding.

**Evidence:** the call site proving the frequency plus the line doing the work.

**Severity:** `Nit`, except a leak: a `CONFIRMED` leak with the quoted holding place (a closure, a subscription without unsubscribe, a listener without remove) is `Important`. A `CONFIRMED` deep reactive container fed by a high-frequency stream is `Important` too. Its evidence quotes three things: the subscription of each stream it counts, the write into the deep container, and the proof of the rate: a timer interval, a per-frame or per-tick source, a loop, or a source whose own contract or docs name its rate. Several streams: the rate of each counted one is proven, and their sum is the rate. A cascade is quoted link by link, from the write to the dependent that writes again. A subscription alone does not prove the rate; without that proof there is no finding. CPU load is `Important` on the same proof: the rate (a timer interval, a per-frame source, an event the user fires continuously) and the line whose cost grows with the data (a full list, a whole tree, a parse of the whole payload). A long-lived application with a leak or with constant recomputation has broken behavior, not a style issue.

**Not a finding:** extra work off a proven hot path: the code is correct and the user does not feel it ([shape gate](../gates/shape.md#shape-gate)).
