# ui

**You own what the user sees. The reference or the project's own system is the spec; a deviation is fixed or asked, never explained away. The whole component you touch matches its reference, not only the part the task names: a mismatch that predates your change is still yours to fix. An element the reference does not show is not added: fix the existing one.**

Atoms: prove-shippable, small-steps, shared-state, questions, autonomy, ux.

Any flow that changes code decides whether the task touches the UI: your judgment of what the user will see, not file extensions. The answer does not depend on whether the app can run here: a changed color, font, label, layout or field the user sees is `ui` even when the proof will be tests only. Record it always: `jig ui scope ui "<why>"` or `jig ui scope none "<why>"`. `ui`: the UI part of the task follows this flow.

1. Profile: `jig ui matrix` prints the combinations to prove from the `ui` section of `.jig/config.jsonc`. Missing: run `jig init`, show its proposed `ui` key to the user, ask once what it cannot know (theme and locale switches, targets), write the confirmed key. A task may narrow the profile for this run (one target, one width), never widen it silently.
2. References: collect every reference the task holds: design links, screenshots, a Claude design, an old implementation, a text spec. None found and the user did not say there is none: ask once whether a design, screenshot or other reference exists, and wait before any code (afk, atom `autonomy`: nobody to ask, go on with no reference). Record the decision always: `jig ui reference add "<source>" [--covers "<screen or state>"]` per reference, or `jig ui reference none "<reason>"` (the user said none, the user answered none, afk). It writes `.jig/ui/<branch>/references.json` and the `ui-reference` receipt; the other `jig ui` commands refuse to run without it.
3. References exist, before any code: prepare each one into the two formats jig reads, a PNG and a node tree in jig's schema (node, text, fill, font). How to get them from the source is your call: a design tool's MCP or API, a Claude design rendered to PNG with its DOM read into the tree, a screenshot is already an image. When `ui.reference.fetch` is set in `.jig/config.local.jsonc`, `jig ui reference add "<source>"` runs it and attaches both files itself: give the source exactly as the task gives it (the link, not your summary or a local copy). It fails: read its message and fix the cause (the source, a missing file); never replace it with a tree you wrote by hand from a few nodes, which makes `jig ui mockup` pass on nothing. Otherwise `jig ui reference attach <n> --image <png> --tree <json>`. `jig pre-mr` asks this for every listed reference. `--none "<why>"` is only for a reference with no visual form (a text spec): never for a design, a screenshot or an export, even when converting it is work; a design you cannot turn into a tree is a question to the user (afk: write the converter). Looking at the design by eye is not a substitute: without the tree, `jig ui mockup` cannot catch a missed color or font size.
   - A design already exported in another tool's format (a YAML or JSON dump of a design tool, for example in `.figma/`): write a short script that converts it, do not copy nodes by hand. The usual mapping: the node's id and name; its type (text nodes carry their string as `text`, a component instance is `kind: instance`); its first solid fill as `fill` (resolve a fill or style that points to a shared variable to its color); its text style as `font` (family, size, weight, line height); its stroke, size as `bounds`, corner radius, opacity; children in order. Skip what has no visible effect. Check the result against `schema/ui-tree.schema.json` by attaching it: `attach` rejects a tree that does not match.
   - An existing implementation (a migration, a port): screenshots of the old app at the matrix sizes, and the diff must be zero (`--exact`).
   - A text spec: acceptance criteria, each with a visible end state (what the user sees, at which size and in which state), shown to the user before code.
   - Never edit the reference, its captures or the capture script to make a comparison pass; a reference that looks wrong goes in your reply.
4. No reference: the implicit reference is the project's design system (its tokens, its shared components from `ui.components.dirs`) and the nearest similar screen, which you name before code. Tokens: jig reads only its own table in the W3C Design Tokens (DTCG) JSON format, with the name, the value per theme and the names code uses to refer to it; build it yourself or let `ui.tokens.command` print it. A new screen: two prototypes behind a switcher (flows/prototype.md), the user picks; afk: you pick, and the reply lists the other and why.
5. Reuse inventory before code: which shared components the change uses, which element the design needs that none covers. A new shared component only with the user's consent (afk: build the screen from the existing ones and list the need). A raw element that `ui.components.map` names is a defect, not a shortcut. A second control for what an existing control already sets (a new section, field or flag next to the old one) is a defect too, even where the reference does not draw that panel: change the existing control to do the job, and renaming the old one does not make them different.
6. Build with atom `ux`: one component at a time, shared primitives first; parallel owners each get their own worktree and never write the same file (atom shared-state). Run the app where SKILL.md says (Where the app runs).
7. Prove, after your last edit:
   - `jig ui reuse`: no raw element on changed lines;
   - `jig ui mockup <n>` per reference with a tree, one run per node your change touches (run without `--component` to list the nodes): the drawn component with the code paths of the component and its spec, and the panel or form whose fields you changed with `--ui` and its code paths, so a control the reference does not show reads as NOT IN MOCKUP: colors, fonts, labels, a swapped frame; tokens are looked up from the token table. A color the code reaches only through a token reads as MISSING until jig has the table: with no `ui.tokens`, build it from the project's token source (step 4) and pass it with `--tokens <file>`; never rewrite tokens into literals to silence the check;
   - `jig ui prove [--states <use case>,...]` with the states the reference or the criteria show (hover, empty, loading, error): every matrix combination on the running app, a layout audit and a pixel diff against each image reference. With `ui.driver` set, jig drives the app itself; without it, capture the combinations yourself with the app control tool and run `jig ui prove --collect`.
   Each prints what failed and exits 1: fix the cause and rerun, never narrow `--root` or `--target` to hide a failure. An audit error is a defect, a pixel difference is evidence for the reviewer. Combinations that only a person can check (native targets): name them to the user.
8. Reviewer rounds, at most 3: role `ui-reviewer` with the references (or the implicit one), the shot of each combination, the outputs of step 7 and the base branch. Re-verify each finding yourself against its shot region or `file:line`; fix the real ones, keep a Dropped list with the evidence for the rest, rerun step 7 after a fix. Findings still open after round 3 go to the user.
9. Deviations from the reference: a design can be outdated, or the task wants something else the owner forgot to say. Fix the obvious misses first: a color, font size or label that differs from the reference in the component you touch is a miss, whether or not your change caused it, and so is a control the reference does not show. Fix them before `jig pre-mr`, never stop with them open. That the fix changes how existing screens or saved data look is the point of matching the reference, not a reason to ask: name it in the merge request. A control the reference lacks is solved by making the existing control do the job, even when that changes its meaning; the old meaning goes in the merge request. Ask only where the task text itself contradicts the reference, once, as a list: per finding what the reference shows, what the code shows and your guess. Afk: decide by your guess and mark it "decided by the agent". An accepted deviation is a line in `.jig/ui/<branch>/deviations.md`: the difference, the reason, who accepted it; the evidence page shows it.
10. Merge request: `flows/mr.md`. The description is written by skill `jig-visual-mr`; the key images go in Evidence as Before (the reference) and After (the result), uploaded to the merge request (`references/forge.md`), never committed images. Give the user the path of `.jig/ui/<branch>/index.html`.

What `jig pre-mr` checks: receipts only, it runs nothing: `ui-scope` always; with `ui`: `ui-reference`, `ui-reference:<n>` per listed reference (step 3, files attached or `--none`), `ui-reuse` (when `ui.components.map` is not empty), `ui-mockup` per reference with a tree, `ui-matrix` (when proof on a running app is possible: `ui.driver` or `--collect`).

Reply: the profile and references (or the implicit one), the reuse inventory, the combinations proven with their exit codes, the reviewer rounds and what was dropped, the deviations and who accepted them, the manual targets, the evidence page.
