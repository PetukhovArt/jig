# Atom index

- `autonomy` (`atoms/autonomy.md`): Apply when you are about to ask the human 'should I do X?'. Reversible work proceeds without asking; only irreversible actions wait for a human. Proceed, then present.
- `change-impact` (`atoms/change-impact.md`): Apply before you change code other code depends on. Find what the change could break outside the diff, name the one fact the change is safe because of, and prove that fact as far as the risk demands.
- `boundaries` (`atoms/boundaries.md`): Apply when wiring validation, error handling, adapters or imports across modules. Guard at system boundaries (network, storage, IPC, CLI, config), trust internal types, keep business logic pure, and cross module boundaries only through their public interface.
- `comments` (`atoms/comments.md`): Apply when you add, keep or review a code comment. The code is the source of truth: a new comment is allowed only if it is a license header, a TODO with a ticket id, JSDoc that says more than the signature of a public API, a constraint forced by external code with a link, or a tool directive.
- `context-window` (`atoms/context-window.md`): Apply when context fills up: large outputs, long files, repeated reads, fan-out work. Route bulk reading to subagents and keep summaries, not raw payloads, in the main thread.
- `dead-code` (`atoms/dead-code.md`): Apply when deleting code believed unused, or reviewing a diff that leaves an export, file or branch nothing reaches. Code is dead only when every reachability signal agrees.
- `design-alternatives` (`atoms/design-alternatives.md`): Apply when facing a novel interface, data shape or architectural decision with no precedent in the codebase, or when a new requirement lands in an existing design. Get the data structures right first, explore two or three shapes, and redesign as if the requirement had been there from day one.
- `docs` (`atoms/docs.md`): Apply when writing, editing or reviewing a Markdown document (README, docs, ADR, glossary). A document earns its place by saying what the code cannot; every claim in it must match the code today.
- `domain-model` (`atoms/domain-model.md`): Apply when writing stateful logic, designing types, or when code branches a lot on the same shape. Encode the domain in a structure (a union, a state machine, a registry) instead of scattered conditionals, and make illegal states unrepresentable.
- `effects` (`atoms/effects.md`): Apply when writing or reviewing reactive code (Vue, React, Solid, signals, stores). Derive state instead of syncing it with effects; an effect is for talking to the outside world, not for wiring one piece of state to another.
- `lessons-to-checks` (`atoms/lessons-to-checks.md`): Apply when you catch yourself writing the same instruction a second time, or see a recurring correction or review finding. Encode the rule as structure (architecture, a type, a lint whose message names the fix, a test) instead of more text.
- `evidence` (`atoms/evidence.md`): Apply to every claim in a reply or report. Each claim carries its evidence or its label in the same sentence: measured, inferred, or guess. Never hand the human a check you could run yourself.
- `why-this-number` (`atoms/why-this-number.md`): Apply before you trust, report or act on a measured number: a speedup, a regression, a latency, a throughput, an eval score. Find what limits it and rule out that it measured something other than the work you think.
- `interface-design` (`atoms/interface-design.md`): Apply before you write code that crosses a function boundary: a new or changed signature, exported type or module surface. Design a deep module: a small interface over much hidden behavior, a seam only where behavior varies, the caller's usage first, two shapes compared by depth.
- `do-less` (`atoms/do-less.md`): Apply when sizing a change, adding an option or abstraction, or sequencing an addition. Bias toward deletion and the smallest change that solves the problem; remove dead weight first, then build on the simpler base.
- `automate-repeats` (`atoms/automate-repeats.md`): Apply to any non-trivial edit, migration, analysis or check. Build the tool that does it or proves it (codemod, script, generator) instead of working by hand; the tool is the artifact a reviewer can rerun.
- `one-way` (`atoms/one-way.md`): Apply when introducing a new API, abstraction or way of doing a task while old ones exist. There is one way to do each task: migrate every caller and delete the old way in the same wave; keep a compatibility layer only while an intermediate state ships to a shared branch.
- `patterns` (`atoms/patterns.md`): Apply when designing a module interface with two or more variants, or when untangling complex code: a switch on type, an instanceof chain, duplicated conditional creation, an import cycle. Map the problem to the pattern that solves it.
- `prove-shippable` (`atoms/prove-shippable.md`): Apply after completing a task, before declaring done. Verify against the real artifact (run the feature, read the actual value, inspect the diff), not a proxy, a self-report or 'it compiles'.
- `questions` (`atoms/questions.md`): Apply before you ask the human anything. A fact has one right answer and is looked up, not asked; a fork you can settle by running something is settled by a prototype or experiment; only product or taste calls go to the human, always with your recommendation.
- `reader-cost` (`atoms/reader-cost.md`): Apply when shaping or reviewing code that is hard to trace. Count the layers between a question and its answer and the state a reader must hold; collapse one-caller wrappers and shrink mutable scope.
- `root-causes` (`atoms/root-causes.md`): Apply when debugging. Trace each symptom back to the first place the system went wrong and fix it there. A guard is a fix only when the state it handles is legitimate. If two fixes sharing one premise fail the same check, test the premise.
- `shared-state` (`atoms/shared-state.md`): Apply when concurrent actors, modules or runs might write the same file, key, branch or state object, or when a command must survive crashes and retries. Eliminate the sharing first; make every step converge to the same end state on rerun.
- `smells` (`atoms/smells.md`): Apply when judging whether a hunk is a code smell. Each smell is a heuristic with a known fix, never a hard violation; report it as 'possible <smell>'.
- `tests` (`atoms/tests.md`): Apply when you write, change, keep or review a test. Assert what the code's users can observe, so the test fails when that behavior breaks and keeps passing when only the internals change. No test is the default.
- `typescript` (`atoms/typescript.md`): Apply when reading or editing TypeScript. Model with the type system: sum types over flag combinations, branded primitives, parsing at boundaries, no lies to the compiler, exhaustive handling.
- `small-steps` (`atoms/small-steps.md`): Apply to multi-step work and to how you stack commits and merge requests. Break the work into small units that each end in a verifiable state, check each before the next, and order delivery so the sequence proves itself to a reviewer.
